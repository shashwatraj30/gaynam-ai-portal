# COMPARE_B - Old platform (localhost:3000) vs new Gyanam AI Portal (127.0.0.1:8091/app/)
Scope: catalogue sections 6 (Upload/Intake), 7 (Draft Judgment studio), 9 (Audit & Security), 10 (Roles), 11 (Docs/exports), 12 (Sync/Corpus), 13 (Cross-cutting) plus the shell/role items F001-F015 that overlap them.
Method: code reading only (no UI run). Paths are relative to the portal root `gyanam/Gyanam_AI_Portal`. `FE` = `frontend/app/js`, `BE` = `backend`.
Status key: PRESENT (equal or better) / PARTIAL / MISSING. Priority: P1 = old-platform user would notice it missing; P2 = useful; P3 = nice to have.

Headline gaps (P1):
1. Saved-draft version history UI (backend `/api/drafts/{id}/versions` + `api.draftVersions` exist, nothing in the UI calls them).
2. "+ Insert Precedent" into sections 10/15 (F055) and the 3 "later" claim checks are missing in the studio; no per-section regenerate/reject.
3. Sign-in is still passwordless (`/api/auth/sso/nluj`), `/api/auth/login` still mints tokens for any name, legacy tokenless header mode and several endpoints are still open; user suspension is not enforced.
4. Seal has no real digital signature ("not connected"); no 65B / 63 BSA certificate.
5. Audit: IP column dropped, no Excel/PDF export, CSV capped at 500 rows; DPDP redaction regexes unchanged (spaced Aadhaar only, no names).
6. Dark theme missing (F111); FIR samples missing (F041).

# Part 4 - Ideas to go beyond the legacy platform (tied to the Google SOW / human-in-the-loop)
1. **Per-section regenerate / reject / accept** in the studio: three buttons per section ("Regenerate", "Reject (restore previous)", "Accept"), with per-section state (Machine-written / Edited by human / Accepted by <name>) shown as chips; a draft cannot be sent for review until all 15 are Accepted. Store section states in `draft_content_json.review_state`.
2. **Tracked changes** between AI text and human edit: keep `ai_original` per section, show word-level diff (insert/delete colours), "Accept all / reject all", export DOCX with real Word tracked changes (python-docx revisions via w:ins/w:del).
3. **Source-to-output traceability**: every sentence in sections 4-13 links to a source (uploaded page + bounding box for OCR, or judgment id + paragraph for authorities). Click -> `sourcePanel` + `pdfViewer` (components already exist in `ui/source-panel.js`, `ui/pdf-viewer.js`). Fail the "pre-approval checks" if a quoted passage is not found verbatim in the source.
4. **Review workflow**: reviewer assignment, comment threads anchored to a section, "changes requested" reasons, SLA/due date, notifications (in-app + e-mail), "My queue" page. Uses `RETURNED` with reason.
5. **Digital signature & seal**: eSign/DSC (PAdES) with timestamp authority, QR code on printed gazette linking to `#/verify/<hash>`; sealed PDF stored immutably; public verify page.
6. **Saved searches and alerts**: save Research filters (text, court, year, status) with name; schedule alerts "new judgments matching X" and "a precedent I cited was overruled" (alerts page exists); saved audit filters for Auditor.
7. **Reports**: PDF/Excel/CSV export for audit, research results, citation-verification certificate, sync history, per-matter bundle; scheduled monthly compliance report e-mailed to the Auditor with ledger head hash.
8. **Configurable roles**: roles and permissions in a DB table; Admin UI (Chamber) to create a role, tick permissions from the catalogue (SEARCH, DRAFT_FULL, FINALIZE_JUDGMENT, ...), clone from existing, and a per-user override; every change is a ledger event with reason; show the effective permission matrix per page ("what can this role open?").
9. **Real authentication**: OIDC/SAML SSO with the NLU Jodhpur IdP + MFA; session list ("devices signed in") with revoke; password policy for local fallback; failed-login lockout; Auditor read-only break-glass rule.
10. **DPDP tooling**: redaction preview with accept/reject per span and a "redaction log" kept with the matter; data-subject request register; retention schedule with auto-purge of uploads after N days; consent record view; export of "personal data held" for a matter.
11. **Ledger hardening**: periodic anchoring of the head hash (e-mail/WORM/second DB), signed blocks (HMAC with key outside DB), downloadable verifier script and documented algorithm so an external auditor can recompute offline.
12. **Model governance**: record on each generated section the model name/version, prompt hash, retrieved authorities, and temperature; show "AI involvement" statement in the exported judgment; allow Admin to set which engine (template / local LLM / API) is permitted per role.
13. **Hindi and bilingual drafting**: bilingual headings in DOCX, Hindi OCR, side-by-side translation of a section with human verification flag.
14. **Quality gates before seal** (extend `buildPreChecks`): all citations resolve and none overruled; no OCR-noise sections; all 15 accepted; reviewer different from author (four-eyes); outcome set; names redacted where required.
15. **Matter bundle & collaboration**: per-matter documents tab (uploaded originals + redacted copies), activity timeline (exists in `matter.js` history drawer), presence indicator ("Adv. Mathur is editing section 11") and section locks to avoid 409 conflicts.
16. **Command palette actions**: "Open draft #", "Verify citation …", "Start new matter", recent items.
